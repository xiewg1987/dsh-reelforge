# ReelForge 开发任务拆分（5 个任务）

> 上游文档：`../ReelForge-设计方案.md`（v4，参照源 `SwotAtmk/infinite-creation`）。
> 本目录是**实施拆分**，不是新设计——每个任务的契约都指向主文档的章节号，不重复发明。
> **每个任务都是一份可独立投给 DSH 会话的说明书**：末尾「给 DSH 的任务说明」整段可直接粘贴。

---

## 1. 为什么拆成 5 个

主文档 §12 的 M0–M5 是**里程碑**（按能力成熟度切）。实施要的是**可并行的任务**（按交付边界切）。
两者的差别：M0–M5 里 M0 是「查契约」，它不产出功能，却卡住后面全部；把它单列会让并行度归零。

所以拆法是：**把「查契约 + 搭骨架 + 定死所有跨任务契约」合成一个前置任务**，剩下 4 个按能力轴切。

| 任务 | 一句话 | 交付边界 | 主文档出处 |
| --- | --- | --- | --- |
| **T1 契约与骨架** | 把插件装上 DSH，并把**所有跨任务共用的契约**定死 | 能装、能跑、能写、不能造假 | §4 · §5.2 · §6.1 · §6.5 · §6.7 |
| **T2 一致性底座** | 上下文三键 + 10 类资产 + 参考素材装配 + 技能引擎 | 一致性锚点能算出来，技能能读 | §2.3 ④⑥ · §6.3 · §6.4 · §7.4 · §8.2 |
| **T3 生成执行** | kind × 位置的执行器 + 四阶段编排 + 探测门槛 | 能真出图出片，能续跑不重复计费 | §7.1–§7.3 · §8.1 · §8.4 · §8.5 · §8.6 |
| **T4 合成交付与回滚** | ffmpeg 合成 + 交付物 + 变更日志三级回滚 + 降级 | 一章端到端出片，错了能退 | §6.6 · §9.1–§9.3 |
| **T5 工作台与技能工厂** | 右栏 7 页签 + 对话 7 类消息行 + 工作流确定性解析 | 人能看懂、能干预；工作流能被读懂 | §8.3 · §10.1–§10.4 · §10.6 |

## 2. 依赖图与执行波次

```text
        ┌──────────────────────────┐
        │  T1 契约与骨架（必须先做） │
        │  装上 DSH + 冻结全部契约   │
        └────────────┬─────────────┘
                     │ 冻结契约表（见 §3）
      ┌──────────────┴──────────────┐
      ▼                             ▼
┌───────────────┐            ┌───────────────┐
│ T2 一致性底座  │            │ T3 生成执行    │
│ 上下文/资产    │            │ 执行器/编排    │
│ 参考装配/技能  │            │ 探测/门槛      │
└───────┬───────┘            └───────┬───────┘
        │  refs 接口 ────────────────► │
        │  （T2 定，T3 消费）            │
        └──────────────┬──────────────┘
                       ▼
      ┌────────────────────────────────────┐
      │  T4 合成交付与回滚  ‖  T5 工作台    │
      │  ffmpeg/交付/回滚/降级 ‖ 页签/消息行 │
      │            ‖ 工作流工厂               │
      └────────────────────────────────────┘
```

| 波次 | 任务 | 并行性 | 关键路径 |
| --- | --- | --- | --- |
| ① | T1 | **独占**（没装上什么都做不了） | ✔ 关键路径 |
| ② | T2 ‖ T3 | **可并行**——T2 定 `refs` 接口，T3 按该接口消费 | ✔ 关键路径 |
| ③ | T4 ‖ T5 | **可并行**——T5 前端可先用 T1/T2 的读接口 + mock 数据 | T4 是关键路径 |

**波次 ② 的接缝只有一处**：`resolveRefs()`（T2 产出，T3 消费）。T2 必须在**头两天**把这个函数的入参/出参冻结，否则 T3 会自己造一套参考装配逻辑，最后两边对不上（这类漂移在 §6.5 那种「静默丢弃」的场景里最难查）。

## 3. 跨任务冻结契约表（**最重要的一张表**）

主文档 §2.2 定的纪律：**`src/core/constants.js` 是唯一枚举来源**。下表是它的「二阶」——**5 个任务共同依赖、一经冻结不得改**的契约。

| # | 冻结契约 | 冻结于 | 后续任务怎么用 | 改动的代价 |
| --- | --- | --- | --- | --- |
| **F1** | **包名三处完全相等**（`package.json.name` / `cordis.patch.yml` Loader 行 `name` / 构建产物 `window.__ModuleLoader__.load({id})` 的 `id`） | T1 | 全部任务**只引用**这个 id | **client 半静默不加载**，控制台不报错，右栏就是没这个 Tab（R7） |
| **F2** | 右栏 Tab **kind = `reelforge-workbench`** | T1 | T5 注册 Tab 时按此 kind | kind 一经发布**不可改名**（R8），改了老用户的 Tab 全变「这类内容还没有可用的查看方式」 |
| **F3** | `project.json` 三层结构 + **内容字段 / 产物字段**白名单 | T1 | T2/T3/T4 **只写内容字段**；产物字段只有渲染阶段能写 | 写入门禁一旦松动，外部就能伪造「已生成」状态（§6.5） |
| **F4** | **13 个 ReelForge 工具 + 2 个只读技能工具的 id 与入参 schema**（`reelforge.import_novel` / `set_storyboard` / `save_context` / `update_shot` / `create_asset` / `update_asset` / `bind_asset` / `run_stage` / `regenerate_shot` / `assemble_chapter` / `set_chapter_music` / `rollback` / **`update_plan`** + `skill` / `skill_reference`） | T1（`update_plan` 于实现阶段合流时补入，见下方「冻结契约变更记录」） | T2–T5 填实现，**不改 id、不加参数** | 模型靠这些 id 形成稳定调用习惯，改名=模型重新学 |
| **F5** | `WorkflowSpec` 形状：`{id, kind, name, description, sourceFile, roles, media?, outputs, prune?}` | T1 | T3 实现执行器、T5 实现解析器，都按此形状 | 规格形状一变，执行器与解析器两边同时改 |
| **F6** | `resolveRefs(shot, assets, ctx) → { images[], audios[], tags[], order[], warnings[] }` | T2（波次②头两天） | T3 **只消费**，不自己实现装配 | 装配逻辑两处实现 = 一致性必然崩 |
| **F7** | 阶段模型：`STAGES = [llm, image, tts, video]`，固定顺序串行；**video 硬依赖 image、软依赖 tts** | T3 | T4/T5 按此呈现依赖与降级 | 依赖语义是 infinite-creation 的核心，乱序会静默降质 |
| **F8** | `src/core/constants.js` 是**唯一枚举来源** | T1 | 全部任务**引用**它，**不得**在自己文件里再写一份枚举 | 三处枚举漂移 = 界面显示的选项和实际能跑的对不上（§2.2） |
| **F9** | **对话消息行的文件所有权与 payload 形状**：`src/host/chatEvents.js` 归 **T5**（7 个 kind 的事件定义 + `conversation.chat.node` 视图注册）；`src/core/deliverPayload.js` / `src/core/changelogPayload.js` 归 **T4**（纯数据组装）；`src/core/planPayload.js` 归 T5。三行 payload 形状见 `T5-工作台与技能工厂.md` §2.4.4 | T5（波次③头两天） | T4 按 T5 的形状产出 payload；**形状不同时改 T4，不改 T5 的视图** | T4 与 T5 同波次并行，两个任务改同一个 `chatEvents.js` 必然合并打架 |

> **执行纪律**：F1–F9 一旦冻结，**任何任务都不得单方面修改**。要改先在主文档 §2.2 / §6.1 / §6.5 / §8.1 更新，再同步到所有任务。

## 4. 每个任务都要遵守的宿主硬规则

主文档 §4.4 的 R1–R14 对 5 个任务**全部适用**，这里只列最容易在实现中踩的：

| # | 规则 | 落到哪个任务 |
| --- | --- | --- |
| R1 | 会话日志是唯一事实源，插件内存只是派生缓存 | T1（投影）、T3（状态）、T4（快照） |
| R2 | **不要 append 新 `type` 的会话事件**；插件私有数据放存储服务 | T1、T4 |
| R4 | 只用最弱的够用机制；需要等用户决策就用 `tools/pre-execute` 返回 `ask` | T1（工具注册）、T3（触发类工具） |
| R5 | 可调值放插件 `Config`（`cordis.patch.yml`），用户的 patch 层能在升级中存活 | T1、T3 |
| R6 | 插件 UI 是宿主 UI 的一部分：用宿主主题 token、locale、布局范式 | T5 |
| R9 | client bundle 的 `require` 受 purity gate 限制 → 第三方库必须**整包内联** | T5 |
| R10 | 入口**异步** `require.async('./client.<名字>.js')`；分片与入口必须**同一 rev**；**构建脚本不再产出的旧分片必须手工删** | T1、T5 |
| R11 | 不抢宿主已占用的快捷键 | T5 |
| R12 | 快捷键 id 必须匹配 `/^[a-z][a-zA-Z0-9-]*(?:\.[a-zA-Z][a-zA-Z0-9-]*)+$/` | T5 |
| R13 | 一般不声明 `web:linux` | T5 |
| R14 | 两个 Tab 共享数据时，状态放**模块级单例** + `useSyncExternalStore` | T5 |

## 5. 每个任务的 Definition of Done

5 个任务**共用**以下收尾条件，缺一不算完成：

1. `cordis_inspect_query` 的三查（`--service Tool` / `--event Event` / `--slots Slots`）结论**写进任务报告**——不查就猜，是本项目最容易出的错。
2. 新增的宿主注册项**有清理函数**，且清理函数同时留在插件自己的 effect 里（R3）。
3. 可调值进 `Config`，**不硬编码**地址、端口、路径、模型名（R5）。
4. `src/core/` 里的纯逻辑**有单测**；宿主专属逻辑留在 `src/host/`，两者不互相渗透（§5.2）。
5. 枚举**只从 `src/core/constants.js` 取**（F8）。
6. 失败路径**要说清缺什么、给什么替代**——不许静默降质（§9.3）。
7. 触发类工具（`run_stage` / `regenerate_shot` / `assemble_chapter` / `rollback`）**走 `ask` 人工授权**（R4）。
8. 报告里列出「**偏离主文档之处 + 原因**」，供主控合并判断。
